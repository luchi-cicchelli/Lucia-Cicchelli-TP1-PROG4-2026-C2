La base · 1

La foto grande

Bijou es la web de un cine: cartelera, compra de entradas con butacas en vivo, candy bar, puntos, y un panel para el admin y el empleado.

La app está hecha con Angular 19 (componentes standalone, sin NgModules) y usa Supabase como backend: base de datos Postgres, login, archivos, tiempo real y una función en la nube. Está publicada en Vercel y se puede instalar como PWA.

Pensalo como un cine de verdad

Las pantallas (features/) son la boletería y el hall: lo que ve el cliente. Los componentes (shared/) son los muebles que se repiten: la butaca, el cartel de la película, las estrellitas. Los servicios (core/services/) son la oficina de atrás: nadie los ve, pero ahí se busca la información y se hacen las cuentas. Y Supabase es el depósito con llave: guarda todo y decide quién puede entrar a cada estante.

Cómo viaja un dato

PantallaEl usuario toca «Pagar» en checkout.
→
ServicioComprasService.confirmar() arma el pedido.
→
SupabaseLlama a la función confirmar_compra (RPC).
→
PostgresValida, calcula el precio y guarda todo junto, con RLS.

La vuelta es igual pero al revés: la base devuelve el id de la compra, el servicio se lo pasa a la pantalla, y la pantalla navega a /compra/:id para mostrar el QR.

Quién hace qué

TipoQué haceQué NO hace
Pantallas
features/		Guardan lo que se ve (signals), reaccionan a los clicks y le piden datos a un servicio.No arman consultas a la base.
Componentes
shared/		Dibujan lo que reciben por input() y avisan con output() cuando el usuario toca algo.No saben de qué pantalla vienen ni hablan con Supabase (salvo subir-imagen, que usa el servicio de Storage).
Servicios
core/services/		Hablan con Supabase, transforman los datos y guardan estado compartido (por ejemplo la sesión).No tocan el HTML.
Base
supabase/		Guarda, valida y decide permisos (RLS). Las operaciones importantes son funciones de Postgres.No confía en lo que manda el navegador: recalcula todo.
Para la defensa

«Separé la app en tres capas: pantallas, componentes reutilizables y servicios. Los componentes nunca hablan con Supabase directo, lo hacen los servicios. Y la seguridad no depende del front: está en la base, con RLS y funciones que validan todo.»

La base · 3

Cómo arranca la app

Desde que abrís la URL hasta que ves la cartelera.

  1. index.html se descarga con una etiqueta vacía <app-root>. Todavía no hay nada para ver.
  2. main.ts ejecuta bootstrapApplication(AppComponent, appConfig): le dice a Angular cuál es el componente principal y con qué configuración arrancar.
  3. app.config.ts registra los providers, o sea las herramientas que va a usar toda la app:
    • provideRouter(routes, withComponentInputBinding()): las rutas, y que los parámetros de la URL (como :id) lleguen al componente como input().
    • provideHttpClient(withInterceptors([supabaseInterceptor])): el cliente HTTP con el interceptor.
    • { provide: LOCALE_ID, useValue: 'es-AR' } + registerLocaleData: fechas y plata en formato argentino («jueves 8 de octubre», «$ 8.500»).
    • provideServiceWorker('ngsw-worker.js', …): la PWA (solo en producción).
  4. AppComponent es el marco fijo: la barra de carga, el navbar, el aviso de estrenos y el <router-outlet>, que es el hueco donde se dibuja la pantalla de la ruta actual.
  5. AuthService se crea y se suscribe a onAuthStateChange de Supabase. Cuando llega el evento INITIAL_SESSION (la sesión que estaba guardada, o ninguna) resuelve la promesa listo. Los guards esperan esa promesa antes de decidir.
  6. El router mira la URL, corre el guard, descarga el código de esa pantalla (lazy) y la dibuja.
main.ts
bootstrapApplication(AppComponent, appConfig)
  .catch((err) => console.error(err));
¿Por qué listo?

Supabase tarda un instante en leer la sesión guardada. Sin esa espera, si recargás en /perfil el guard pensaría que no estás logueada y te mandaría al login aunque sí lo estés.

Lazy loading

Ninguna pantalla se importa arriba de todo: cada ruta usa loadComponent: () => import('…'). Angular arma un archivo JS separado por pantalla (un chunk) y lo descarga recién cuando entrás. Un cliente nunca descarga el código del panel de admin.

{
  path: 'pelicula/:id',
  canActivate: [ingresoGuard],
  loadComponent: () =>
    import('./features/pelicula-detalle/pelicula-detalle.component')
      .then((m) => m.PeliculaDetalleComponent)
}

Los cuatro guards

Son guards funcionales (CanActivateFn): funciones que usan inject() para pedir el AuthService y el Router. Todos esperan auth.listo y devuelven true (pasa) o un UrlTree (redirige).

  • ingresoGuard: alcanza con tener sesión, aunque sea de invitado. Si no, al login con ?volver= para regresar después a donde ibas.
  • authGuard: hace falta cuenta de verdad (no invitado).
  • rolGuard(roles): es una fábrica: una función que devuelve un guard. Así el mismo código sirve para ['admin'] y para ['empleado','admin']. Si el rol no está en la lista, te manda al inicio.
  • sinCuentaGuard: si ya entraste con cuenta, el login no tiene sentido: te manda a tu inicio según el rol (rutaInicio(): admin → /admin, empleado → /empleado/escaner, cliente → /).
Para la defensa

«Los guards son comodidad, no seguridad: esconden pantallas. Si alguien llama a la base a mano, lo frena RLS. Por eso cada permiso está dos veces: en el guard para la experiencia, y en la base para la seguridad.»

El navbar según el rol

navbar lee signals del AuthService (tieneSesion(), esEmpleado(), esAdmin()) y con @if muestra solo los links que te corresponden. En el celu se convierte en un menú hamburguesa.

Herramientas de Angular

Los temas de la cursada y dónde aparecen en Bijou.

Signals: el estado de la pantalla

Un signal es una caja con un valor que avisa cuando cambia. Todo lo que se dibuja sale de signals:

  • signal(): un valor que se puede cambiar con .set() o .update(). Ej.: busqueda, pestania, generosElegidos en el inicio.
  • computed(): un valor que se calcula a partir de otros y se recalcula solo. Ej.: filtradas (películas que coinciden con la búsqueda y los géneros), o toda la cuenta del precio en el checkout.
  • effect(): corre código cuando cambia un signal. Ej.: en AppComponent, cuando aparece un usuario con cuenta, busca sus avisos de estreno.
  • input() / output(): la versión con signals de @Input/@Output. Ej.: mapa-butacas recibe butacas y emite elegir.
home.component.ts (resumido)
readonly busqueda = signal('');
readonly generosElegidos = signal<ReadonlySet<number>>(new Set());
readonly filtradas = computed(() => {
  const texto = normalizar(this.busqueda().trim());
  const generos = this.generosElegidos();
  return this.enCartel().filter((p) => {
    const coincideTexto =
      !texto || normalizar(p.nombre).includes(texto) || normalizar(p.sinopsis).includes(texto);
    const coincideGenero = generos.size === 0 || p.generos.some((g) => generos.has(g.id));
    return coincideTexto && coincideGenero;
  });
});

Control flow en los templates

Se usa la sintaxis nueva: @if / @else, @for (…; track …) con @empty, @switch / @case (las pestañas del perfil) y @let (en la ficha: @let p = pelicula()!).

Inyección de dependencias

Los servicios son @Injectable({ providedIn: 'root' }): hay una sola instancia para toda la app (por eso la sesión es la misma en todas las pantallas). Se piden con inject(AuthService) o por constructor.

Formularios reactivos

  • Registro: FormBuilder.nonNullable.group con Validators.required, email, minLength(6), y validadores propios: soloLetras (nombre y apellido) y fechaNacimientoValida (no futura), más un validador de grupo que compara las dos contraseñas.
  • Funciones (admin): un FormArray de horarios (se agregan y quitan) y un validador de rango (hasta después de desde, máximo 90 días).
  • Películas, cupones, recompensas, candy: formularios con validaciones de precio, porcentaje, etc.

Directiva propia: appImagenRespaldo

Se pone en un <img>. Con host: { '(error)': 'usarRespaldo()' } escucha el error de carga y cambia el src por img/sin-poster.svg. Si también falla el respaldo, no entra en loop.

Interceptor HTTP

supabase.interceptor.ts mira cada pedido de HttpClient: si va a Supabase, le agrega la apikey y el Authorization: Bearer <token> del usuario, y prende la barra de carga (CargandoService) hasta que termina (finalize).

Detalle fino

La librería supabase-js hace sus propios pedidos con fetch, no con HttpClient. Por eso el interceptor solo actúa en la llamada que sí usa HttpClient: la de la Edge Function avisar-estrenos. Es justamente donde hace falta mandar los headers a mano.

Componentes con input y output

  • selector-fecha y selector-hora: reemplazan el input type="date" por desplegables (lo pidió el cliente). Reciben valor y emiten cambio.
  • subir-imagen: sube el archivo y emite la URL pública.
  • tarjeta-pelicula: recibe pelicula, posicion (el #1, #2, #3), proximamente y compacta (la versión chica del inicio, que se activa con una clase en el host).

Carga diferida de librerías pesadas

jspdf y exceljs se importan con await import('jspdf') recién cuando tocás «Descargar PDF» o «Exportar Excel». Así no agrandan la carga inicial.

Supabase · 6

La conexión y las consultas

Un solo cliente para toda la app, y dos formas de pedir datos: a una tabla o a una función.

El cliente único

core/services/supabase.service.ts
@Injectable({ providedIn: 'root' })
export class SupabaseService {
  public client: SupabaseClient;
  constructor() {
    this.client = createClient(environment.supabaseUrl, environment.supabaseAnonKey);
  }
}

Como es providedIn: 'root', hay una sola conexión y todos los servicios la comparten inyectando SupabaseService. Los datos de conexión están en environments/environment.ts (producción) y environment.development.ts (ng serve).

¿No es peligroso que la clave esté en el front?

No. Es la clave anon / publishable: está pensada para ir en el navegador. Sola no da permisos; lo que se puede hacer lo decide RLS según quién esté logueado. La clave peligrosa es la service role, y esa solo vive en la Edge Function, como secreto de Supabase.

Forma 1: consultar una tabla

Para leer o hacer ABM simples se usa el query builder. Se pueden traer tablas relacionadas en la misma consulta:

cartelera.service.ts: películas activas con sus géneros
this.supabase.client
  .from('peliculas')
  .select('*, pelicula_generos(generos(id, nombre))')
  .eq('activa', true)
  .order('fecha_estreno', { ascending: false });

Forma 2: llamar a una función (RPC)

Todo lo que tiene reglas de negocio o toca varias tablas a la vez es una función de Postgres que se llama con .rpc(). Corre entera en una transacción: o se guarda todo, o nada.

compras.service.ts
const { data, error } = await this.supabase.client.rpc('confirmar_compra', {
  p_funcion_id: funcionId,
  p_sesion: this.sesion,
  p_metodo_pago: metodoPago,
  p_items: …, p_cupon: …, p_usar_credito: …, p_canjes: …
});
if (error) throw error;

Errores

Toda respuesta de Supabase trae { data, error }. Los servicios hacen if (error) throw error y la pantalla lo atrapa con try/catch y lo muestra en un signal error. Los mensajes «lindos» («La venta abre el 15/10», «No te alcanzan los puntos…») salen de los raise exception de las funciones SQL.

Tipos propios (enums)

rol_usuario (cliente, admin, empleado), formato_funcion (2d…5d), idioma_funcion, tipo_butaca, estado_entrada, tipo_cupon, tipo_item_compra, tipo_movimiento_puntos. Un enum hace que la base rechace cualquier valor que no esté en la lista.

Las butacas se crean solas

Cuando el admin crea una sala, el trigger al_crear_sala llama a generar_butacas: filas A–I y L–Q normales (28 por fila: bloques de 4, 20 y 4), una fila accesible en lugar de la J y la K (14 butacas, que se dibujan del doble de ancho) y R, S, T VIP. RLS: quién puede qué

Row Level Security: reglas que Postgres revisa en cada fila, para cada usuario, en cada consulta.

Todas las tablas tienen RLS activado. Sin una política que lo permita, la base responde vacío o error, aunque el pedido venga de la app. Para saber quién pregunta, las políticas usan auth.uid() (el id del token) y dos funciones propias:

  • rol_actual(): busca el rol del usuario en perfiles. Es security definer para poder leer aunque la política de perfiles no lo deje.
  • es_invitado(): lee is_anonymous del token. Un invitado tiene sesión, pero no perfil.

Auth, Realtime, Storage y Edge Functions

Los cuatro servicios de Supabase que usa Bijou, además de la base.

Auth

  • Registro: auth.signUp({ email, password, options: { data: perfil } }). Los datos del formulario viajan como metadata, y el trigger al_crear_usuario (crear_perfil_nuevo_usuario) crea la fila en perfiles. Si no hay perfil, no hay cuenta a medias.
  • Login: signInWithPassword.
  • Invitado: signInAnonymously({ options: { data: { nombre } } }). Es un usuario anónimo de Supabase: tiene token, pero el trigger no le crea perfil.
  • Salir: signOut({ scope: 'local' }): cierra solo en este navegador.
  • La sesión vive en signals del AuthService: session, perfil y derivados como estaLogueado, esInvitado, rol, esAdmin, edad.
  • traducirError() pasa los errores de Supabase a castellano («Mail o contraseña incorrectos»).

Realtime: las butacas en vivo

En el checkout, cada función tiene un canal funcion-<id> de tipo Broadcast. Cuando alguien reserva o suelta una butaca, la app manda un mensaje cambio al canal; los demás que están mirando la misma función lo reciben y vuelven a pedir estado_butacas.

compras.service.ts
escucharCambios(funcionId, alCambiar) {
  return this.supabase.client
    .channel(`funcion-${funcionId}`)
    .on('broadcast', { event: 'cambio' }, alCambiar)
    .subscribe();
}
avisarCambio(canal) {
  canal.send({ type: 'broadcast', event: 'cambio', payload: {} });
}

El mensaje no lleva datos: solo dice «algo cambió». El estado real siempre se lee de la base. Por si se pierde un mensaje, además se refresca cada 15 segundos.

Storage

Bucket público imagenes, con carpetas para pósters y para el candy. storage.service.ts sube el archivo con un nombre único y devuelve la URL pública con getPublicUrl. Las políticas de storage.sql dejan ver a todos y subir/cambiar/borrar solo al admin. El componente subir-imagen lo usa y emite la URL con output().

Edge Function: avisar-estrenos

Es código TypeScript que corre en los servidores de Supabase (Deno), no en el navegador. Hace falta porque necesita secretos que no pueden estar en el front: la service role key (para leer los mails de todos) y la API key de Brevo (para mandar mails). La explica la sección 20.

De dónde salen los datos

  • filtradas: enCartel filtrado por el texto del buscador (título o sinopsis) y por los géneros elegidos (chips).

«El filtro es un computed: depende de la búsqueda, de los géneros y de la lista. Si cambia cualquiera, se recalcula solo, sin volver a pedirle nada a la base.»

La «sesión de compra»

Cada pestaña tiene un id al azar (crypto.randomUUID()) guardado en sessionStorage. Las reservas se guardan con ese id: así la base sabe qué butacas son «mías» y cuáles de otra persona, aunque sea un invitado.

Elegir una butaca

  1. El mapa-butacas emite elegir con la butaca tocada.
  2. La pantalla la pinta como «mía» al instante y llama a reservar_butaca, que valida: la función no empezó, la venta ya abrió, la butaca es de esa sala, no está vendida ni reservada por otro y no pasás de 10 por compra.
  3. La reserva dura 10 minutos (todas las de la misma compra vencen juntas) y se ve un reloj. Si llega a 0, se liberan y la pantalla te avisa.

El mapa pinta cada butaca según estado_butacas: libre, vendida, reservada por otro o mía. Las VIP (R, S, T) y las accesibles se ven distintas, y si elegís una VIP, el resumen lo aclara antes de pagar.

El precio final ★

La cuenta que hace confirmar_compra (versión final en invitados.sql). El checkout hace la misma cuenta con computed para mostrarla, pero la que vale es la de la base.

  1. Precio de la entrada general: si la función está en preventa y todavía no llegó el estreno, precio_preventa; si no, precio_base.
  2. Entradas: cada butaca VIP suma precio_vip; las normales y accesibles, el precio general.
  3. Candy: precio × cantidad de cada producto (precios leídos de la base, solo si están activos).
  4. Combos: cada combo suma precio_fijo − precio general, porque la entrada que incluye ya estaba contada en el paso 2.
  5. Canjes de puntos: cada «entrada gratis» resta un precio general. Un producto canjeado se agrega al candy a $0. Hay que tener los puntos.
  6. Cupón: uno solo, el de mayor porcentaje entre el de bienvenida (si es tu primera compra con cuenta) y el código que escribiste. Se aplica sobre el subtotal ya con los canjes.
  7. Crédito a favor (si tildaste usarlo): se descuenta hasta cubrir el total.
  8. Puntos que ganás: floor(total), o sea 1 punto por peso pagado. Solo con cuenta.
subtotal = entradas + candy + Σ(combo − general)
         − entradasGratis × general
total    = subtotal − subtotal × %cupón − crédito
puntos   = floor(total)
Ejemplo

2 butacas normales a $8.500 + 1 combo de $14.000 + 20% de bienvenida:
entradas $17.000 + combo ($14.000 − $8.500 = $5.500) = $22.500 → −20% = $18.000 → ganás 18.000 puntos.

Qué controla la base además

  • Que tus reservas no hayan vencido («Tu reserva venció…»).
  • Combos + entradas gratis ≤ butacas.
  • Método de pago válido (tarjeta de crédito, débito o Mercado Pago; el pago es simulado).
  • Edad mínima, puntos suficientes, cupón vigente (y edad si es de mayores de 50).
  • Al final: crea la compra, una entrada por butaca, los ítems de candy, el historial de puntos, borra las reservas y actualiza puntos, crédito y cupón de bienvenida del perfil. Todo en una transacción.

El QR y el código manual no los genera la app: los pone el trigger generar_codigos_compra al insertar la compra.

Para la defensa

«El front muestra el total con computed para que el usuario lo vea al instante, pero la cuenta oficial la hace confirmar_compra en Postgres, con los precios de la base. Así nadie puede cambiar un precio desde el navegador.»

Asignación de salas ★

El cliente pidió: «quiero poner lunes, martes y viernes a las 18 y que el sistema elija la sala».

En la pantalla

El admin elige película, formato, idioma, precios, días de la semana, uno o más horarios (FormArray) y un rango desde/hasta (máximo 90 días). Un computed (inicios) genera todas las fechas y horas que resultan, sin las que ya pasaron, y las muestra como vista previa antes de crear.

En la base: crear_funciones

  1. Verifica que seas admin, que haya horarios, precios positivos y al menos una sala.
  2. Toma un candado (pg_advisory_xact_lock) para que dos admins no asignen salas al mismo tiempo.
  3. Para cada horario, en orden: calcula el fin (inicio + duración) y busca la primera sala libre, o sea una sala sin funciones que se pisen con ese rango más 30 minutos.
  4. Si para algún horario no hay sala, corta con error y no crea ninguna («No hay salas libres el… (ninguna función se creó)»).
  5. Copia la preventa de la película y anota en el log cuántas funciones creó.

La red de seguridad: exclusion constraint

salas_funciones.sql (resumido)
exclude using gist (
  sala_id with =,
  rango_ocupado(fecha_hora_inicio, fecha_hora_fin) with &&
)

rango_ocupado devuelve el intervalo de la función más 30 minutos para limpiar la sala. La restricción dice: «no puede haber dos filas con la misma sala cuyos intervalos se superpongan (&&)». La base lo impide aunque alguien inserte a mano, saltándose la RPC. Necesita la extensión btree_gist.

Para la defensa

«La RPC elige la sala, y la exclusion constraint garantiza que nunca haya dos funciones superpuestas en la misma sala con menos de 30 minutos de margen. Son dos capas: la lógica y la regla de la base.»

Alertas de estreno

Suscribirse

El boton-alerta (en Próximamente y en la ficha) guarda o borra una fila en alertas_estreno (usuario + película) con alertas.service.ts. Solo para usuarios con cuenta; al invitado le ofrece registrarse.

Aviso 1: mail (Edge Function avisar-estrenos)

  1. El admin toca «Enviar alertas de estreno» en Películas. La app llama a la Edge Function con HttpClient (el interceptor agrega la apikey y el token).
  2. La función revisa que el token sea de un admin.
  3. Llama a alertas_pendientes() (solo la puede usar la service role): alertas no notificadas de películas cuya venta ya abrió y que tienen funciones.
  4. Para cada una manda un mail con la API de Brevo (fetch), con un botón «Comprar entradas».
  5. Solo marca notificado = true si el mail salió; si falló, queda pendiente para el próximo envío.

Aviso 2: dentro de la app nuevo

  1. Cuando entra un usuario con cuenta, un effect() en AppComponent llama a la RPC mis_avisos_estreno.
  2. La RPC devuelve las alertas del usuario con la venta ya abierta y vista_en_app = false.
  3. Se muestra un aviso rosa debajo del navbar («¡Abrió la preventa!» o «¡Ya están las entradas!») con un botón «Comprar».
  4. Al cerrarlo o tocar Comprar, se marca vista_en_app = true y no vuelve a aparecer.

El mail y el aviso se marcan por separado (notificado y vista_en_app), así uno no apaga al otro.

¿Por qué no notificaciones push?

Las push del navegador (Service Worker + claves VAPID) no entraban en el TP, así que se sacaron. Quedó el mail y el aviso al entrar, que no necesitan permisos del navegador.

PWA

Que se pueda instalar como app y que abra rápido.

  • public/manifest.webmanifest: nombre («Bijou Cine» / «Bijou»), color rosa #D4537E, display: standalone (sin barra del navegador) e íconos de 72 a 512 px en public/icons/. Con eso el navegador ofrece «Instalar».
  • Service Worker: provideServiceWorker('ngsw-worker.js', { enabled: !isDevMode(), registrationStrategy: 'registerWhenStable:30000' }). Solo funciona en producción y se registra cuando la app ya cargó (o a los 30 segundos), para no competir con la primera carga.
  • ngsw-config.json: el grupo app (index, JS, CSS) se descarga entero apenas se instala (prefetch); el grupo assets (imágenes, fuentes) se guarda a medida que se usa (lazy).
Por qué a veces ves la versión vieja

El Service Worker sirve la versión guardada y descarga la nueva en segundo plano. La nueva aparece en la siguiente apertura. Por eso, después de un deploy, a veces hay que cerrar la pestaña (o la app instalada) y volver a abrirla.

Los datos (cartelera, butacas) no se guardan en caché: siempre vienen de Supabase, porque tienen que estar al día.

Deploy y librerías

Vercel

  • Cada git push a main hace que Vercel corra ng build y publique dist/.
  • vercel.json tiene un rewrite: cualquier ruta devuelve index.html. Sin eso, recargar en /perfil daría 404, porque ese archivo no existe en el servidor: las rutas las resuelve Angular en el navegador.
  • La base se arma corriendo los .sql en el SQL Editor de Supabase, en el orden del README. La Edge Function se pega en el panel de Supabase con sus secretos (BREVO_API_KEY, MAIL_REMITENTE).

Diseño y scroll controlado

Estilo propio: minimalista, rosa #D4537E, Playfair Display para títulos e Inter para el texto.

  • Variables CSS en styles.css (--rosa-acento, --fondo, --texto…). El modo oscuro redefine esas variables con @media (prefers-color-scheme: dark): sigue lo que tenga elegido el sistema.
  • Responsive: grillas que cambian de columnas, navbar con hamburguesa en el celu y @media en cada pantalla.
  • Fechas y horas con desplegables (selector-fecha, selector-hora), como pidió el cliente.

Scroll controlado nuevo

La página no crece hacia abajo: lo largo scrollea dentro de su recuadro y lo importante queda quieto.

  • app-root mide exactamente el alto de la pantalla (100dvh), el navbar queda fijo y solo el <main> puede scrollear.
  • Las pantallas con listas largas usan la clase .pantalla (ocupa todo el alto) y ponen la lista dentro de .pantalla__scroll. Título, filtros, pestañas y botones quedan siempre a la vista.
  • grid-auto-rows: max-content en el recuadro: cada tarjeta mide lo que su contenido, nunca se achica ni se recorta.
  • Si la pantalla es muy baja, .pantalla tiene un alto mínimo y scrollea el main antes que cortar algo.
  • Ejemplos: en el inicio solo scrollea la grilla de películas; en la compra, el mapa y el candy scrollean y «Tu compra» queda a la vista; en Funciones, las pestañas de días quedan pegadas arriba (position: sticky).

Seguridad: fuerte y débil

Saber decir qué está bien protegido y qué se podría mejorar suma mucho en una defensa.

Lo fuerte

  • RLS en todas las tablas: cada usuario ve solo lo suyo; el admin, todo.
  • Permisos por columna en perfiles: un usuario puede editar sus datos, pero no su rol, sus puntos, su crédito ni su fecha de nacimiento (grant update (nombre, apellido, …)). Así nadie se «cambia la edad» para ver una película +18 o usar el cupón de mayores de 50.
  • Lógica en el servidor: comprar, cancelar, validar QR, crear funciones y cambiar precios son RPC security definer que validan todo y corren en una transacción. El precio lo calcula la base.
  • Concurrencia: FOR UPDATE en el escáner y en la compra, candado en la asignación de salas, exclusion constraint contra funciones superpuestas, on conflict para que dos personas no reserven la misma butaca.
  • Secretos fuera del front: la service role y la clave de Brevo viven solo en la Edge Function, que además verifica que quien la llama sea admin.
  • Storage: todos ven las imágenes, solo el admin sube o borra.

Preguntas de defensa

Tocá cada pregunta para ver una respuesta corta.

¿Por qué standalone y no NgModules?

Es la forma actual de Angular: cada componente declara lo que importa, no hace falta un módulo que los agrupe, y el lazy loading se hace con loadComponent directo.

¿Qué diferencia hay entre signal, computed y effect?

signal guarda un valor que cambiás vos. computed se calcula a partir de otros signals y se actualiza solo (no se puede setear). effect ejecuta algo cuando cambian los signals que lee, por ejemplo buscar los avisos de estreno cuando aparece un usuario.

¿Cómo llega el :id de la URL al componente?

Con withComponentInputBinding() en el router: el parámetro se asigna al input() que se llama igual (id, funcionId). No hace falta ActivatedRoute.

Si saco el guard de /admin, ¿un cliente puede borrar una película?

Vería la pantalla, pero no podría hacer nada: RLS solo deja escribir en peliculas al admin y las RPC verifican rol_actual(). El guard es experiencia, la seguridad está en la base.

¿Qué pasa si dos personas tocan la misma butaca al mismo tiempo?

La reserva es un insert con on conflict do nothing sobre (función, butaca): uno entra y al otro la base le responde «Alguien más está eligiendo esa butaca». Después, por Realtime, todos ven la butaca ocupada.

¿Y si cierro la pestaña en el medio de la compra?

Si salís navegando, ngOnDestroy libera las butacas. Si cerrás de golpe, igual vencen solas a los 10 minutos: cada RPC borra las reservas vencidas antes de trabajar.

¿Dónde se calcula el precio? ¿Puedo pagar menos tocando el JavaScript?

En confirmar_compra, con los precios de la base. La app solo manda qué butacas, productos, cupón y canjes querés. El total que se ve en pantalla es una copia de la misma cuenta, para mostrarla.

¿Cómo funciona el combo si incluye una entrada?

El combo suma su precio fijo menos una entrada general, porque esa entrada ya se cuenta por la butaca. Por eso no se pueden pedir más combos que butacas.

¿Se pueden acumular cupones?

No: se aplica uno solo, el de mayor porcentaje entre el de bienvenida y el que escribiste.

¿Cómo se evita que haya dos funciones a la vez en una sala?

Dos capas: crear_funciones busca una sala libre (con 30 minutos de margen) y una exclusion constraint con btree_gist impide en la base dos rangos superpuestos en la misma sala, aunque se inserte a mano.

¿Cómo se valida un QR una sola vez?

validar_entrada busca la compra con FOR UPDATE, revisa que haya entradas activas y las pasa a validada. Un segundo escaneo encuentra todo validado y responde «ya se usaron el … a las …».

¿Qué es un invitado para Supabase?

Un usuario anónimo (signInAnonymously): tiene token y sesión, pero el trigger no le crea perfil. En la base se lo reconoce con es_invitado(), que lee is_anonymous del token.

¿Para qué una Edge Function si ya tengo RPC?

Para cosas que no pueden pasar por el navegador ni por SQL: mandar un mail a un servicio externo (Brevo) con una clave secreta, y leer datos de todos con la service role. Corre en el servidor de Supabase.

¿Qué hace el interceptor?

Le agrega la apikey y el token del usuario a los pedidos de HttpClient que van a Supabase (la Edge Function) y prende y apaga la barra de carga.

¿Qué ganás con el lazy loading?

Cada pantalla es un archivo aparte que se descarga cuando entrás. La primera carga es más liviana, y un cliente nunca baja el código del admin. Con jspdf y exceljs pasa lo mismo: se cargan con import() recién al exportar.

¿Qué hace que sea una PWA?

El manifest (nombre, íconos, color, standalone) y el Service Worker de Angular, que guarda la app en caché para que abra rápido y se pueda instalar.

¿Por qué el crédito y no devolver la plata?

Lo pidió el cliente: se cancela hasta 2 horas antes y lo pagado queda como crédito para usar en otra compra, junto con otros medios de pago.

Glosario

Standalone
Componente que no necesita un NgModule: declara sus propios imports.
Signal
Valor reactivo: cuando cambia, Angular actualiza lo que depende de él.
computed
Signal calculado a partir de otros; se recalcula solo.
effect
Código que corre cuando cambian los signals que lee.
input / output
Datos que entran a un componente / eventos que salen de él.
Guard
Función que decide si se puede entrar a una ruta.
Lazy loading
Descargar el código de una pantalla recién cuando se entra.
Interceptor
Función que ve y modifica cada pedido HTTP antes de salir.
Pipe
Transforma un valor en el template (148 | duracion).
Directiva
Agrega comportamiento a un elemento existente (appImagenRespaldo).
RLS
Row Level Security: reglas de Postgres que deciden, fila por fila, quién puede leer o escribir.
Política (policy)
Cada regla de RLS: para qué tabla, qué operación y con qué condición.
RPC
Llamar a una función de Postgres desde la app (.rpc('nombre', params)).
security definer
Función que corre con los permisos de quien la creó; la puerta controlada a tablas cerradas.
Trigger
Código de la base que corre solo cuando pasa algo (insert, update, delete).
Transacción
Un conjunto de cambios que se guarda entero o no se guarda.
FOR UPDATE
Bloquea las filas leídas hasta terminar, para que nadie las cambie en el medio.
Exclusion constraint
Regla que impide dos filas «que choquen» (acá: misma sala y horarios superpuestos).
Enum
Tipo con una lista cerrada de valores posibles.
anon key
Clave pública de Supabase, para el navegador. Sola no da permisos.
service role
Clave con acceso total que se salta RLS. Solo en el servidor (Edge Function).
Edge Function
Función TypeScript que corre en los servidores de Supabase.
Broadcast
Mensajes de Realtime entre navegadores conectados al mismo canal.
Bucket
«Carpeta» de Storage donde se guardan archivos.
Service Worker
Script del navegador que guarda la app en caché y la hace instalable.
Manifest
Archivo con nombre, íconos y colores de la PWA.
Rewrite
Regla del servidor que devuelve index.html para cualquier ruta.
